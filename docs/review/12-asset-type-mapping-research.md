## B. HaloPSA API for asset types and fields

Primary evidence (VERIFIED): the official OpenAPI document served by a public Halo demo tenant: `https://halo.haloservicedesk.com/api/swagger/v2/swagger.json` (title "Halo API", the HaloITSM/HaloPSA/HaloCRM REST API, 5.2MB, downloaded and parsed). The apidoc SPA (`https://halo.haloservicedesk.com/apidoc/...`) renders client-side so WebFetch cannot read it; the swagger JSON it loads (`/api/swagger`) is the authoritative source. Every tenant exposes the same at `https://<tenant>.halopsa.com/api/swagger` (INFERRED for other tenants; the path comes from the SPA bundle string "/api/swagger"). halopsa.com redirects to usehalo.com (301).

1. List asset types: `GET /AssetType` returns "List of Xtype". VERIFIED query params: `assetgroup_id`, `can_create_only`, `can_edit_only`, `fixedassetgroups`, `include_current`, `resourcesonly`, `setuplist`, `tickettype_id`, `type`. There is NO `search`, `showall`, `includeinactive` or `includedetails` on this path in the swagger (the PowerShell module HaloAPI lists `-Search`, `-IncludeActive`, `-IncludeInactive`, `-ShowAll`, `-FullObjects` for Get-HaloAssetType, source https://www.powershellgallery.com/packages/HaloAPI/1.23.1/Content/Get%5CGet-HaloAssetType.ps1, VERIFIED to exist, but they are not documented by the API, so treat them as unreliable; filter client-side). `GET /AssetTypeInfo` is an identical-parameter sibling (VERIFIED). INFERRED: `setuplist=true` returns the config-screen list (all types including ones the agent cannot create); test live. The current code already calls `GET assettype` without params and reads `assettypes` (HaloPsaClient.php:416); the response key may be a bare array or `assettypes` (extractList copes).
2. Asset type model "Xtype" (VERIFIED, 214 props): `id`, `name`, `assetgroup_id/_name`, `keyfield_id/_name`, `keyfield2_id/_name`, `keyfield3_id/_name`, `fields: [TypeInfo]`, `field_list: [Field]`, `tab_config`, `inventorynumber_tab`, etc.
   - TypeInfo (VERIFIED): `typeinfo_id`, `id`, `field_id`, `field_name`, `sequence`, `keyfield_id`, `type`, `tab_id/tab_name`, `groupname`, `require_uniqueness`, `regex`.
   - Field (VERIFIED): `id`, `kind`, `typeinfo_id`, `name`, `validate`, `lookup`, `mandatory`, `systemuse`, `sequence`, `parenttype_id/_name`, `tab_*`, `access_level`, `values`, `extratype`, `hint`, `require_uniqueness`, `regex`.
3. Fetch one type's fields: `GET /AssetType/{id}` (path id, query `includedetails`, `fieldsandlayoutonly`, `client_id`, `site_id`, `booking_type`, `start_date`, `end_date`, all VERIFIED). INFERRED: `fields`/`field_list` are only populated with `includedetails=true` (or `fieldsandlayoutonly=true`, which by name returns just fields and layout and is the lighter call). Which of `fields` and `field_list` to use is INFERRED: `field_list[].id` + `name` + `kind` is the cleanest dropdown source; `fields[].field_id`/`field_name` carries the same ids plus `keyfield_id`. Confirm live and normalise both shapes.
4. Writing values: `POST /Asset` body is an ARRAY of `Device` (VERIFIED: `requestBody` schema `array<Device>`; matches HaloPsaClient::createDomainAsset/updateAsset which wrap in a list and the "id present = update" rule, and the search snippet from https://completeit.halopsa.com/apidoc/resources/assets). `Device` has TWO value arrays (VERIFIED):
   - `fields: [FieldHelper]` with `id`, `name`, `value`, `mandatory`, `typeinfo_id`, ... = asset-type "Asset Fields". This is what DomainDash sends today: `{id, value}`.
   - `customfields: [CustomField]` with `id`, `name`, `label`, `type`, `value`, `usage`, ... = "Custom Fields for Assets" (Configuration > Custom Objects), not attachable per type. Halo guides: asset fields "can be added to specific Asset Types"; custom fields "cannot be added/removed per Asset Type" (from https://halopsa.com/guides/article?kbid=1784 via search snippet; page itself 404/redirect to fetch, so SECONDARY evidence).
   - Therefore the "148/149/150/165" ids are only valid in `fields` if they are Field ids of the Domain type. Which id space (`Field.id` vs `TypeInfo.typeinfo_id`) `FieldHelper.id` takes is INFERRED to be `Field.id` (the key the current code and its prior working integration used); the dropdown must send the same id the user sees, so show both in the preview and verify with one live create.
5. Key fields: `Xtype.keyfield_id`, `keyfield2_id`, `keyfield3_id` define which fields feed `Device.key_field`, `key_field2`, `key_field3` (VERIFIED names; semantics INFERRED from names and Halo guide "Three of these can be marked as Key Fields, displayed in lists"). DomainDash hard-codes key_field=domain, key_field2=expiry, key_field3=nameservers: this only works if the chosen type's key fields match. Plan item below.
6. Inventory number: `Device.inventory_number` (VERIFIED); GET /Asset has `inventory_number` and `search_inventory_number_only` filters (VERIFIED), which `findAssetByInventory` could use instead of broad `search`.
7. Asset group: `GET /AssetGroup` (query `type`, `istree`, `includetypesforgroups`), `Xtype.assetgroup_id`; `GET /AssetType?assetgroup_id=` filters (all VERIFIED). Useful as an optional grouping in the picker; not required.
8. Field catalogue: `GET /Field` (query `kind`, `type_id`), `GET /Field/{id}`, `GET /FieldInfo` (query `typeid`, `systemid`, `iscustomfieldsetup`, `includevalues`, `extratype` ...), `GET /FieldInfo/{id}` (all VERIFIED present). For asset customfields use `GET /Asset?include_custom_fields=<csv ids>` (VERIFIED param) to read, and `FieldInfo` filtering only if a live tenant proves the usage code.
9. Paging: `page_size`, `page_no`, `pageinate` (sic) on list calls (VERIFIED on /Asset; AssetType has none, the list is small).
10. Auth: bearer token via client_credentials; scopes unspecified (INFERRED: `all`/`admin` scope probably needed to read `AssetType` setup; the current client already reads `assettype`, so the same token works).

## C. IT Glue equivalent (VERIFIED against https://api.itglue.com/developer/, downloaded and parsed)

- `GET /flexible_asset_types`: filters `filter[id]`, `filter[name]` (exact string), `filter[icon]`, `filter[enabled]` (true/false/1/0); `sort` = id|name|created_at|updated_at (prefix `-` to invert); `page[number]`, `page[size]`; `include=flexible_asset_fields`. Attributes include `name`, `description`, `icon`, `enabled`, relationships `flexible-asset-fields`.
- `GET /flexible_asset_types/:id` with `include=flexible_asset_fields` returns the fields in `included[]` (type `flexible-asset-fields`).
- `GET /flexible_asset_types/:flexible_asset_type_id/relationships/flexible_asset_fields` lists fields; also `GET /flexible_asset_fields/:id`.
- Field attributes (VERIFIED from the example): `flexible-asset-type-id`, `order`, `name`, `kind`, `hint`, `decimals`, `default-value`, `tag-type`, `required`, `use-for-title`, `expiration`, `show-in-list`, `name-key`, `created-at`, `updated-at`. Doc: "The name-key attributes of fields can be used to POST new flexible assets." Kinds: Checkbox, Date, Header, Number, Select, Text, Textbox, Upload, Tag, Percent, Password (Header/Step also exist per the use-for-title note).
- Traits written on POST/PATCH `/flexible_assets` under `attributes.traits` keyed by `name-key` (matches ItGlueClient::createFlexibleAsset/updateFlexibleAsset). `kind` matters: `Text` = single line, `Textbox` = rich text (HTML OK for the dns trait), `Date` expects Y-m-d, `Tag` needs linked-record ids (DomainDash cannot fill a Tag field with a string).
- Rate limit: 3000 requests per 5 minutes, 429 beyond (VERIFIED); config uses 400/min.
- Current selection in DomainDash: id typed by hand; no lookup by name; trait keys typed by hand with defaults. No validation.

## E. Implementation plan

### E1. Halo settings UX (Settings > HaloPSA, replaces the 4 number inputs)
1. Card "Domain asset type" with button "Load asset types". Calls `GET /admin/settings/halo/asset-types` -> `[{id,name,assetgroup_name,keyfield_names?}]`; renders a searchable `<select>` (alphabetical, "Domain" pre-selected if exactly one case-insensitive name match, or the stored id). Stored in `halo.asset_type_id` (+ `halo.asset_type_name` for display).
2. On select (or on load when an id is stored), call `GET /admin/settings/halo/asset-types/{id}/fields` -> `{fields:[{id,name,kind,mandatory,source:'field'|'custom'}], keyfields:[{slot:1..3,id,name}]}` (backend calls `GET /AssetType/{id}?includedetails=true` (or `fieldsandlayoutonly=true`), normalises `field_list` (preferred) and `fields`, strips to id/name/kind).
3. Mapping table: one row per DomainDash data point (Domain name, Expiry date, Name servers, WHOIS/notes) with a `<select>` of fields plus "Do not sync". Auto-suggest by normalised name/label (e.g. contains `expiry|expire|renew` -> expiry, `name server|nameserver|ns` -> nameservers, `whois` -> whois, `domain` -> domain); mark suggestions as "suggested", user confirms. Show data type warnings (e.g. expiry mapped to a non-date `kind`) as hints only.
4. Optional key-field helper: show the type's key fields 1-3 and what DomainDash will write into them; stop hard-coding key_field2/3 (see E3).
5. "Preview payload" button: dry run that renders the exact `fields` array for a sample domain without calling Halo POST (client-side from the mapping, or `POST /admin/settings/halo/preview` taking a domain id). A "Test" that creates a real asset is NOT recommended.
6. Fallback: collapsible "Advanced: enter field ids manually" keeps the 4 numeric inputs, bound to the same `halo.asset_field_ids`; the dropdown writes the same keys, so `assetFieldIds()` stays the single reader.
7. Storage shape (backward compatible): `halo.asset_type_id`, `halo.asset_type_name`, `halo.asset_field_ids = {domain,expiry,nameservers,whois}` (unchanged), optional `halo.asset_field_labels = {domain: {name, kind}}` for display. Absent keys keep the 148/149/150/165 defaults.
8. Validation (SettingsController): `halo.asset_type_id nullable|integer|min:1`, `asset_type_name nullable|string|max:180`, existing ids. Cross-check on save (when Halo is reachable, tolerate failure): each mapped field id must belong to the selected type's fields; reject duplicates (two data points -> same field).

### E5. Risks and open questions
1. Halo field-id space (`Field.id` vs `TypeInfo.typeinfo_id` vs `FieldHelper.id`) is not documented: verify on a live tenant with one create before shipping; show ids in the UI so users can compare with what works today (148...).
2. `fields` vs `customfields`: a user may pick a Custom Field (Custom Objects) rather than an asset-type Field. Only fields from the selected type's `field_list` should be offered; label them clearly; if a tenant stores domain data in `customfields` the pusher would need a second array (out of scope unless live check shows it).
3. GET /AssetType may need elevated scopes, may omit inactive types, and has no search param: client-side filter, show an error with the Halo status text when 401/403.
4. Mandatory Halo fields (`key_field3` is mandatory per comment) mean unmapped/"Do not sync" can make creates fail; surface `Field.mandatory` in the UI and block saving a mapping that leaves a mandatory field unmapped (warn, do not block, for fields outside the four data points).
5. Changing the mapping changes the sync hash, so every domain re-pushes on next run (rate limit 120/min Halo, 400/min IT Glue); show "N domains will be re-synced" and respect `push_budget_seconds`.
6. IT Glue PATCH deletes traits it is not given; ItGlueClient already merges existing traits, keep that when keys are remapped (old trait keys remain until cleaned: do not delete).
7. IT Glue `Tag`/`Select`/`Upload` kinds cannot take a string; the picker must not offer them (or warn).
8. Large lists: render all rows with DOM nodes can be slow beyond a few thousand; add windowing or cap at 500 visible with "show more" if needed.
9. Existing tests in tests/Feature/SyncReliabilityTest.php (:561, :574, :655) and IntegrationClientsTest (:37) reference the current setting keys and form field names; keep names stable.
10. Security: the new JSON endpoints must be behind the admin settings middleware (not `sync.run` only), CSRF for the settings POST, error messages through `SyncErrorSanitizer`, no raw vendor payloads to the browser, and `throttle`.
11. `getHaloDomains` loads `Domain::with('client')->get()` unbounded: acceptable for now, but pair with server-side pagination if domain counts reach tens of thousands.
