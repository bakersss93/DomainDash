# Task 2 - Synergy Wholesale and Vocus WSM client review

Scope: `app/Services/Synergy/SynergyWholesaleClient.php`, `app/Services/Vocus/VocusWsmClient.php`, `vocus-api/`, all callers under `app/`, `routes/`, `config/`, and how credentials are stored. Read-only review. No code was modified.

Evidence base:
- Synergy: API Documentation v3.18 PDF (downloaded, 180 pages, read via pdftotext). I also fetched the live WSDL from `https://api.synergywholesale.com/?wsdl` (HTTP 200, 275 KB) and compared it with the repo copy `app/wsdl/synergy.wsdl`. Page references below are PDF page numbers, which match the printed numbers.
- Vocus: uploaded WSDL and XSD (the XSD is byte-identical to `vocus-api/.../Schemas/WholesaleServiceManagement.xsd`; the WSDL differs only in line endings). I read the three uploaded PDFs: Main (v8.5.0), Examples and Sandbox. I also read the TCAS catalogue and the Data Types PDF from `vocus-api/`. The FIBRE, DIR and OPER product catalogues are not in the repo, so those parameters are checked only against the Examples PDF.
- PHP `ext-soap` is not installed in this sandbox, so no SOAP runtime behaviour could be executed. Items that depend on runtime behaviour are labelled "inference" or listed under Unverified claims.

## 1. Summary

**Synergy.** The client is a thin `__soapCall` wrapper. It has four structural problems.
1. Three write operations use SOAP operation names or parameter names that do not exist in the vendor WSDL or docs. These are `registerDomain` (the real operation is `domainRegister`), `purchaseHosting` (the real one is `hostingPurchaseService`), and `transferDomain` with `authCode` and flattened contact keys. Domain registration, hosting purchase and domain transfer therefore cannot work as written.
2. The client never inspects `status`. Synergy reports failures as a normal response with `status=ERR_*`, not as a SoapFault (p.9). Every write path (DNS add, update and delete, nameservers, renew) treats "no exception" as success. DNS record "update" is implemented as delete then add, so a failed add loses the record.
3. Two methods called by callers do not exist: `bulkDomainInfo` (the nightly scheduled job) and `getNameserversAndConfig` (the DNS page). The nightly Synergy sync job can never succeed.
4. The WSDL source is fragile and not configurable. The default path points at a gitignored file that does not exist, the bundled WSDL is stale, there is no endpoint or sandbox override, and there are no timeouts.

**Vocus.** The session login, SOAP envelope construction and TCAS polling match the docs. The gaps are in error handling and operational behaviour.
- The ErrorCode is read from the wrong place in the fault detail, so the WSM-4005 session-expiry retry never fires.
- There is no rate limiting. The docs set 5 requests per 10 seconds, but sync loops call `getService` once per service and swallow every error.
- The sandbox cannot be used with the current TLS settings. The sandbox uses self-signed HTTPS and a hosts-file override, and the client has no CA option.
- ResponseType and async states are mishandled in callers. For example, any `SUCCESS` poll flips a service to ACTIVE, even after a cancel.
- Input validation in the controllers contradicts the Data Types limits.

**Both.**
- Secrets are stored in plaintext in the `settings` table.
- `AuditLogger` writes old and new settings values unredacted, so API keys land in `audit_logs`.
- Hosting passwords and cPanel SSO URLs are written to the application log (`ServicesController`).
- The `vocus-api/` directory holds "Commercial and in confidence" vendor PDFs and is committed to git.

Counts: Critical 2, High 9, Medium 17, Low 9 (table below).

## 4. Unverified claims

1. **PHP SoapFault `detail` shape (VOC-01).** I could not run PHP SOAP here (`ext-soap` missing). The vendor docs clearly show the ErrorCode nested under a `Fault`/`FaultResponse` element inside `<detail>`, so `$e->detail->ErrorCode` is almost certainly not populated. The exact property path PHP produces (`detail->FaultResponse->ErrorCode` versus another wrapper, given the WSDL declares the fault message) is inference. Confirm by running a request against the sandbox without logging in (the WSM-4005 test case, Sandbox p.3) and dumping `$e->detail`.
2. **Effect of unknown array keys (SYN-01/02/03).** In WSDL mode PHP SoapClient ignores array keys that are not part of the request type, and the server then reports missing mandatory fields. The exact `errorMessage` per call was not observed (no credentials, no network writes). The wrong operation names are certain: `registerDomain` and `purchaseHosting` do not appear in the live or bundled WSDL.
3. **`updateNameServers` with empty `nameServers` (SYN-13).** The docs say `nameServers` is mandatory; whether Synergy tolerates an empty array when `dnsConfig` is 2/3/4 is not documented.
4. **Single-element `domainList` decoding (SYN-15).** Based on the existing `normalizeSoapEntries` comment in the repo and known PHP SOAP behaviour; not reproduced.
5. **`hoidList` vs `domainList` for `listHosting` (SYN-19).** The docs contradict themselves (p.108 vs p.109). The code uses `hoidList` and I could not confirm it against a live response. The live WSDL type for `listHostingResponse` was not resolved by my parser.
6. **Synergy test/sandbox environment.** The v3.18 PDF does not mention one; I did not verify whether Synergy offers an OTE/test endpoint outside the document.
7. **Vocus FIBRE/DIR/OPER parameters.** Only the TCAS catalogue and Data Types PDF are in the repo. FIBRE `Create`/`Get` parameters, DIR `BROADBAND`/`STANDARD` plan IDs, `StartRecordID` for `NOTIFICATIONS`, and the OPER `AUTH-LOG`/`DISCONNECT` forms (VOC-12) were checked only against the Examples/Data Types PDFs, not against the product catalogues. `StartRecordID` exists in Data Types, but the Examples request uses `StartDateTime`.
8. **Rate limit value.** Main p.4 says 5 requests per 10 s; Sandbox p.3 says the flood trigger is more than 100 per 10 s. The production value was not confirmed; I used the stricter one for the recommendation.
9. **`Cookie` header via stream context (Vocus).** `buildSoapClient` passes `JSESSIONID` through `stream_context['http']['header']`. PHP SoapClient normally honours this, but `$client->__setCookie('JSESSIONID', ...)` is the documented way; I did not test which works. (Not logged as a finding.)
10. **Synergy WSDL staleness.** The 7-operation difference was computed by diffing `<operation name=...>` lists between the live WSDL (fetched today) and `app/wsdl/synergy.wsdl`. Whether those operations are enabled for this reseller is unknown.
11. **No production data or credentials were used.** No requests with real `resellerID`/`apiKey`, Vocus certificate or AccessKey were made. Nothing was written to any vendor system.
